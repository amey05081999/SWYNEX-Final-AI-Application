# AI-Powered Customer Support Ticket Classifier

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/amey05081999/SWYNEX-Intelligent-Feature/blob/main/customer_support_ai_prototype.ipynb)

A proof-of-concept that classifies customer-support messages into `Billing`, `Technical Issue`, `Account Access`, or `General Inquiry`. It demonstrates zero-shot classification, evaluation, failure analysis, and an optional Gradio interface.

> **Status:** Educational prototype, not production-ready. Upload `customer_support_ai_prototype.ipynb` to the repository's `main` branch for the Colab badge to open the notebook.

## 1. Problem

Support teams receive requests about different issues and need to route them to the right team. This prototype predicts one category from a message to help with first-pass triage.

- **Intended users:** Customer-support agents and team coordinators.
- **AI task:** Single-label text classification.
- **Potential benefit:** Reduce repetitive manual sorting while retaining human oversight.

## 2. Data Source and Constraints

The notebook contains a small, hand-written set of example messages with expected labels. This data verifies the workflow; it is not representative of real support traffic.

Constraints include a small sample, only four categories, possible ambiguous or mixed-intent messages, model download/runtime requirements, and limited linguistic variation. Use approved, representative, de-identified data for any serious evaluation.

## 3. Method

The prototype uses Hugging Face Transformers with the pretrained `facebook/bart-large-mnli` zero-shot classification model.

1. Receive a support message.
2. Score it against the four candidate labels.
3. Return the highest-scoring category and scores for all categories.
4. Flag a top score below `0.60` for human review.

The model is not trained on the notebook's small dataset. The `0.60` threshold is a demonstration heuristic, not a validated safety boundary. Model scores are not calibrated probabilities.

## 4. Evaluation and Success Criteria

The notebook calculates:
- **Accuracy** — fraction of predictions matching the expected labels.
- **Precision and recall** — per-category error and coverage measures.
- **Macro F1-score** — unweighted F1 average across categories.
- **Confusion matrix** — which labels are mistaken for one another.

It includes qualitative cases for vague, mixed-intent, and out-of-scope inputs.

### Proposed targets for a larger held-out dataset

- Accuracy ≥ 0.85
- Macro F1-score ≥ 0.80
- Recall ≥ 0.75 for every category
- Human review available for uncertain or ambiguous messages

These are targets, not claimed results. Report metrics produced by your own run. A tiny hand-written dataset cannot establish robust real-world performance. Use a separate validation set to tune thresholds and preserve a final test set for evaluation.

## 7. Failure Cases and Mitigations

| Failure case | Risk | Mitigation |
|---|---|---|
| Vague message, e.g. “It is broken.” | Insufficient information | Ask a clarifying question or route to human triage. |
| Mixed billing and login issue | Single label can discard part of the request | Use multi-label classification or let an agent choose the primary issue. |
| Out-of-scope request | Four labels may force an irrelevant prediction | Add and evaluate an `Other / Out of scope` label. |
| Similar label wording | Results may depend on candidate descriptions | Compare label descriptions on validation data. |
| High score but incorrect prediction | Score may be mistaken for certainty | Audit errors and validate thresholds on representative data. |
| New vocabulary or product changes | Model performance can drift | Monitor errors and re-evaluate periodically. |

## 8. Limitations

- Small, manually written examples make metrics unstable.
- The model may misread typos, local expressions, sarcasm, short messages, and domain-specific language.
- One label cannot fully represent requests containing multiple issues.
- Scores are not calibrated probabilities.
- The prototype is not connected to a ticketing system or customer database.
- No formal bias audit, calibration study, or large-scale latency test has been performed.
- No production-level accuracy or business impact is claimed.

## 9. Ethics, Privacy, and Human Oversight

- **Data minimization:** Use synthetic or approved, de-identified messages. Never enter passwords, payment-card details, authentication tokens, or unnecessary personal data.
- **Human accountability:** Treat predictions as decision support. Have a person review uncertain, mixed-intent, sensitive, or consequential cases.
- **Transparency:** Make clear to agents that the category is model-generated and may be wrong.
- **Fairness and accessibility:** Test relevant languages, dialects, writing styles, and accessibility-related communication patterns before use. Do not assume equal performance without evidence.
- **Security:** Do not expose confidential tickets through public demo URLs. Apply access controls and retention policies before using real data.
- **Monitoring:** Track privacy-preserving error statistics, allow corrections, and investigate systematic mistakes.
- **Scope:** Do not use this prototype alone to decide refunds, eligibility, account sanctions, or other consequential outcomes.
